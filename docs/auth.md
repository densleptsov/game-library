# Аутентификация и авторизация (JWT)

## Зачем нужен этот документ

Описывает, как устроена аутентификация в API: как выдаётся токен, что в нём
внутри, как он проверяется, что делать при утечке. Этот документ —
единственный источник правды по auth. При расхождении с кодом — прав документ.

## Что такое JWT

**JWT (JSON Web Token)** — компактный способ передать подписанные данные
между клиентом и сервером. Это не шифрование, а **подпись**: содержимое
читаемо всем, но изменить его нельзя, не сломав подпись.

JWT состоит из трёх частей, разделённых точками:

```
header.payload.signature
```

Пример реального токена:
```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
eyJzdWIiOiIxIiwiZXhwIjoxNzkwMDAwMDAwLCJpYXQiOjE3ODk5OTgyMDB9.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

### Часть 1. Header (заголовок)
Base64-декодируется в:
```json
{ "alg": "HS256", "typ": "JWT" }
```
- `alg` — алгоритм подписи. У нас **HS256** (HMAC + SHA-256, симметричный).
- `typ` — тип токена, всегда `JWT`.

### Часть 2. Payload (данные)
Base64-декодируется в:
```json
{ "sub": "1", "exp": 1790000000, "iat": 1789998200 }
```
Это **не шифрование** — любой может зайти на `jwt.io` и прочитать содержимое.
Подпись гарантирует только одно: данные не подделали.

### Часть 3. Signature (подпись)
Считается так (упрощённо):
```
HMAC_SHA256(
  base64(header) + "." + base64(payload),
  SECRET_KEY
)
```
Сервер при каждом запросе:
1. Разделяет токен на три части.
2. Берёт header и payload, пересчитывает подпись со своим `SECRET_KEY`.
3. Сравнивает с присланной подписью. Не совпало — токен подделан → 401.
4. Проверяет `exp` — не истёк ли.
5. Извлекает `sub` — это ID пользователя.

## Параметры токена

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| Алгоритм подписи | HS256 | Симметричный, один секрет — проще для монолита |
| Время жизни (access token) | 30 минут | Компромисс: не перелогиниваться каждые 5 минут, но и не держать вечный токен |
| Секрет (`SECRET_KEY`) | 48+ байт, base64 | Генерируется один раз, хранится в .env |
| Поле `sub` | ID пользователя строкой | Стандарт требует строку (`"1"`, а не `1`) |
| Поле `exp` | Unix timestamp UTC | Время, после которого токен невалиден |
| Поле `iat` | Unix timestamp UTC | Когда выдан (для аудита и дебага) |
| Refresh token | не используем (пока) | Для MVP избыточно, добавим при необходимости |

### Почему 30 минут

- **Слишком коротко (5 мин)** — пользователю придётся логиниться каждые 5 минут, UX плохой.
- **Слишком долго (24 часа)** — если токен утечёт, атакующий имеет сутки доступа.
- **30 минут** — компромисс. При истечении пользователь просто логинится снова.

В будущем добавим **refresh token** (живёт 7–30 дней) — тогда access-токен
можно сделать совсем коротким (5–15 минут), а обновлять его через refresh.
Для MVP не нужно, усложнит код и тесты.

### Как сгенерировать SECRET_KEY

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Пример вывода (у тебя будет другой — и это правильно, не используй чужой):
```
Yq8Xf3nLw9K2mP4vB7cR1tE6sH5jD0aZ... (около 64 символов)
```

**Никогда не коммить это значение в Git.** Оно хранится только в `.env`
(который в `.gitignore`) и в CI-секретах.

## Поток аутентификации

### Регистрация
```
Client                                  Server
  │                                       │
  ├── POST /auth/register ──────────────► │
  │   {username, email, password}         │
  │                                       │ 1. Проверить username/email не заняты
  │                                       │ 2. Захешировать пароль (bcrypt)
  │                                       │ 3. Сохранить User в БД
  │ ◄──── 201 {id, username, email} ────  │
```

### Логин
```
Client                                  Server
  │                                       │
  ├── POST /auth/login ─────────────────► │
  │   {username, password}                │
  │                                       │ 1. Найти User по username
  │                                       │ 2. Проверить bcrypt.verify(password, hash)
  │                                       │ 3. Сформировать payload {sub, exp, iat}
  │                                       │ 4. Подписать HS256 + SECRET_KEY
  │ ◄──── 200 {access_token, ...} ──────  │
  │                                       │
  │  (клиент сохраняет токен в память)    │
```

### Защищённый запрос
```
Client                                  Server
  │                                       │
  ├── GET /library ────────────────────► │
  │   Authorization: Bearer <token>       │
  │                                       │ 1. Извлечь токен из заголовка
  │                                       │ 2. Проверить подпись (SECRET_KEY)
  │                                       │ 3. Проверить exp (не просрочен?)
  │                                       │ 4. Достать sub → загрузить User из БД
  │                                       │ 5. Передать User в ручку
  │ ◄──── 200 [entries...] ─────────────  │
```

### Что происходит при истечении токена
```
Client                                  Server
  │                                       │
  ├── GET /library (просроченный токен) ► │
  │                                       │ 1. Проверка подписи — OK
  │                                       │ 2. Проверка exp — FAIL (истёк)
  │ ◄──── 401 {"detail":"Token expired"}  │
  │                                       │
  │  (клиент должен залогиниться снова)   │
```

## Реализация

### Хеширование пароля

**Библиотека:** `passlib` с backend `bcrypt`.

```python
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(plain: str) -> str:
    return pwd_context.hash(plain)

def verify_password(plain: str, hashed: str) -> bool:
    return pwd_context.verify(plain, hashed)
```

**Что происходит при `hash` (упрощённо):**
1. Генерируется случайная соль (16+ байт).
2. Соль + пароль → bcrypt-хеш (медленный по дизайну).
3. Результат упаковывается: `$2b$12$<salt><hash>`.

**Что происходит при `verify`:**
1. Из хеша вытаскивается соль.
2. Считается bcrypt(соль + введённый пароль).
3. Сравнивается с частью хеша. Совпало — пароль верный.

**Почему bcrypt, а не SHA-256:**
- SHA-256 **быстрый** — миллиарды операций в секунду. Идеален для атакующего (брутфорс).
- bcrypt **медленный по дизайну** — настраиваемое число раундов (12 = 2^12 итераций).
  Один хеш — ~100–300 мс. Легитимному пользователю ок, атакующему — 1000 лет перебора.
- bcrypt включает соль автоматически. У SHA-256 нужно вручную добавлять, иначе одинаковые пароли → одинаковые хеши.

### Создание токена

**Библиотека:** `python-jose[cryptography]`.

```python
from datetime import datetime, timedelta, timezone
from jose import jwt

def create_access_token(user_id: int, expires_minutes: int) -> str:
    now = datetime.now(timezone.utc)
    payload = {
        "sub": str(user_id),                              # обязательно строкой
        "iat": int(now.timestamp()),
        "exp": int((now + timedelta(minutes=expires_minutes)).timestamp()),
    }
    return jwt.encode(payload, SECRET_KEY, algorithm="HS256")
```

### Проверка токена

```python
from jose import jwt, JWTError, ExpiredSignatureError

def decode_token(token: str) -> dict:
    try:
        return jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
    except ExpiredSignatureError:
        raise HTTPException(401, "Token expired")
    except JWTError:
        raise HTTPException(401, "Could not validate credentials")
```

**Важно:** в `jwt.decode` всегда указываем `algorithms=["HS256"]` явным списком.
Иначе есть известная уязвимость: атакующий может подсунуть `alg: none` в header,
и некоторые старые библиотеки принимают неподписанные токены.

### Извлечение текущего пользователя (FastAPI dependency)

Псевдокод того, что появится на этапе 3:

```python
from fastapi import Depends, HTTPException
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

bearer = HTTPBearer(auto_error=False)

def get_current_user(
    creds: HTTPAuthorizationCredentials = Depends(bearer),
    db: Session = Depends(get_db),
) -> User:
    if creds is None:
        raise HTTPException(401, "Not authenticated")
    payload = decode_token(creds.credentials)
    user = db.get(User, int(payload["sub"]))
    if user is None:
        raise HTTPException(401, "Could not validate credentials")
    return user
```

Использование в ручке:
```python
@router.get("/library")
def get_library(current_user: User = Depends(get_current_user)):
    ...
```

## Безопасность: угрозы и меры

| Угроза | Как защищаемся | Что НЕ делаем |
|--------|----------------|---------------|
| Утечка SECRET_KEY | В .env, .gitignore, CI-секреты | Не коммитим в репозиторий |
| Слабый SECRET_KEY | Генерация `secrets.token_urlsafe(48)` | Не пишем `"secret"` руками |
| Брутфорс пароля | bcrypt (медленный) | Не используем SHA-256 |
| Rainbow tables | Автоматическая соль в bcrypt | Не хешируем без соли |
| Утечка пароля через БД | Хранится только хеш | Не храним plain-пароль |
| Подделка токена | HS256 + проверка подписи | Не отключаем проверку |
| `alg: none` attack | Явно передаём `algorithms=["HS256"]` | Не доверяем `alg` из header |
| Просроченный токен | Проверка `exp` автоматически (jose) | Не отключаем `exp` |
| Раскрытие чужой записи | Фильтр `WHERE user_id = current.id` | Не полагаемся на `entry_id` |
| User enumeration | Одинаковый 401 при неверном логине/пароле | Не подсказываем «юзер не найден» |
| Пароль в логах | Не логируем тело `/auth/*` | Не пишем `logger.info(request.body)` |
| Токен в URL | Только заголовок `Authorization` | Не принимаем `?token=...` |

### Что осознанно НЕ делаем (для MVP)

- **Rate limiting** (защита от брутфорса по сети) — добавим позже, сейчас не критично для локального проекта.
- **2FA (двухфакторка)** — вне скоупа.
- **Блокировка аккаунта после N неудачных попыток** — тоже вне скоупа.
- **Refresh token** — обсудили в блоке 2.
- **Blacklist отозванных токенов** — требует хранилища (Redis), усложняет.

Всё это фиксируем как «future work». На этапе 6 при написании security-тестов
мы проверим только то, что реализовано.

### Чек-лист безопасности перед деплоем

- [ ] SECRET_KEY сгенерирован случайно, длина 48+ байт.
- [ ] .env в .gitignore.
- [ ] .env.example в репозитории с пустыми значениями.
- [ ] В коде нет паролей/секретов хардкодом.
- [ ] `/docs` открыт только в dev (в prod — отключить или защитить).
- [ ] CORS настроен для конкретных origins (не `*`).
- [ ] Логи не содержат паролей и токенов.
- [ ] Все ручки `/library/*` фильтруют по `current_user.id`.

## Что будем тестировать

Фиксируем список auth-тестов заранее, чтобы на этапе 6 не выдумывать.

### Позитивные
1. Регистрация нового пользователя → 201, поля корректны, пароль не в ответе.
2. Логин с верными данными → 200, есть access_token, token_type=bearer.
3. Запрос `/auth/me` с валидным токеном → 200, это тот же пользователь.
4. Запрос защищённой ручки с валидным токеном → 200.

### Негативные — регистрация
5. Регистрация с занятым username → 409.
6. Регистрация с занятым email → 409.
7. Регистрация с коротким паролем (< 8) → 422.
8. Регистрация с невалидным email → 422.
9. Регистрация с username с недопустимыми символами (`"иван"`, `"a b"`) → 422.

### Негативные — логин
10. Логин с неверным паролем → 401.
11. Логин с несуществующим username → 401, **то же сообщение**, что в тесте 10.
12. Логин с пустым паролем → 422 (валидация).

### Негативные — токен
13. Запрос защищённой ручки без заголовка `Authorization` → 401.
14. Запрос с заголовком `Authorization: Bearer` (без токена) → 401.
15. Запрос с токеном неправильного формата (`"garbage"`) → 401.
16. Запрос с токеном, подписанным **другим** SECRET_KEY → 401.
17. Запрос с **просроченным** токеном → 401, `"Token expired"`.
18. Запрос с токеном, где `sub` указывает на удалённого пользователя → 401.
19. Запрос с токеном, у которого испорчена подпись (последний символ заменён) → 401.

### Специальные
20. Два разных пользователя не видят данные друг друга (проверка row-level security).
21. `expires_in` в ответе логина = 1800 (30 минут в секундах).

**Итого:** ~21 тест только на auth. Из них ~4 позитивных и ~17 негативных.
Соотношение — нормальное для security-критичной области.
