# Стек технологий

## Принципы выбора

Это пет-проект для изучения автотестирования на Python. При выборе инструментов
руководствуемся правилами:

1. **Python-first** — минимум JS/HTML/CSS, максимум Python. Учим один язык.
2. **Минимум магии** — инструменты, где видно, что происходит «под капотом».
3. **Продакшн-подобность** — стек должен быть похож на то, что используют
   в реальных командах (чтобы опыт переносился на работу).
4. **Быстрый старт** — рабочее приложение за вечер, а не за неделю.
5. **Путь к росту** — от SQLite к PostgreSQL, от Streamlit к React — без
   переписывания всего с нуля.

## Язык и окружение

| Компонент | Выбор | Версия |
|-----------|-------|--------|
| Язык | Python | 3.11+ |
| Изоляция зависимостей | venv (стандартный) | — |
| Менеджер пакетов | pip + requirements.txt | — |
| Форматирование | ruff format | latest |
| Линтинг | ruff check | latest |

**Почему Python 3.11+**
- Актуальные фичи: match-выражения, улучшенные ошибки, скорость.
- Совместимость со всеми библиотеками (FastAPI, SQLAlchemy 2.0, Playwright).

**Почему venv, а не poetry/pipenv**
- venv встроен в Python — не надо ставить ничего лишнего.
- requirements.txt прост и понятен новичку.
- Poetry — мощнее, но добавляет свой синтаксис (`pyproject.toml`,
  lock-файлы), что отвлекает от изучения темы автотестов.
- Перейдём на poetry, когда проект вырастет.

**Почему ruff, а не flake8 + black + isort**
- Ruff делает всё это одним инструментом, в 10–100 раз быстрее.
- Один конфиг вместо трёх.
- Стандарт 2024+.

## Backend

| Компонент | Выбор | Назначение |
|-----------|-------|------------|
| Веб-фреймворк | FastAPI | REST API, роутинг, валидация |
| ASGI-сервер | Uvicorn | Запуск приложения |
| Валидация | Pydantic v2 | Схемы запросов/ответов |
| ORM | SQLAlchemy 2.0 | Работа с БД через Python-классы |
| Миграции | Alembic | Версионирование схемы БД |
| JWT | python-jose[cryptography] | Подпись и проверка токенов |
| Хеширование паролей | passlib[bcrypt] | Хранение паролей |
| Настройки | pydantic-settings | Чтение .env |

### FastAPI, а не Flask или Django

- **Swagger из коробки** — `/docs` генерируется автоматически из типов.
  Для автотестов это золото: не надо вручную писать документацию API.
- **Async-first** — современный подход, легко писать конкурентные ручки.
- **Pydantic внутри** — валидация тела запроса и query-параметров бесплатно.
- **Dependency Injection** — элегантная передача `db`, `current_user` в ручки.
- **Flask** — минималистичный, но для REST надо допиливать (flask-restful,
  marshmallow). Django — тяжеловесный, «батарейки в комплекте», много
  магии, не нужной для API-only проекта.

### SQLAlchemy 2.0, а не сырой SQL или Tortoise ORM

- **SQLAlchemy** — стандарт де-факто. Знание переносится на любую работу.
- **2.0** — новый синтаксис с типизацией (`Mapped[int]`, `mapped_column()`),
  ближе к современному Python.
- **Сырой SQL** — быстро, но неудобно: ручное экранирование, никакой
  переносимости между SQLite и PostgreSQL.
- **Tortoise ORM** — асинхронный, но менее популярный, меньше материалов
  на русском.

### Alembic, а не `create_all()`

- `Base.metadata.create_all()` — создаёт таблицы, но **не умеет менять**
  существующие (добавить колонку, изменить тип).
- Alembic — версионирование схемы: каждая миграция = отдельный файл с
  описанием изменений. Как git, только для структуры БД.
- Сейчас кажется лишним. Через месяц, когда захочешь добавить поле —
  поймёшь ценность.

### python-jose, а не PyJWT

- Оба работают. `python-jose` чуть более популярен в связке с FastAPI
  (используется в официальном туториале FastAPI по auth).
- `[cryptography]` — extra с нативной криптографией, работает быстрее
  и поддерживает больше алгоритмов.

### passlib[bcrypt], а не hashlib или bcrypt напрямую

- `hashlib` — не подходит для паролей (нет соли, слишком быстро).
- `bcrypt` напрямую — работает, но passlib даёт единый интерфейс
  (можно поменять алгоритм на argon2 одной строкой).
- passlib автоматически: солит, хеширует, проверяет.

### pydantic-settings, а не os.environ

- `os.environ["SECRET_KEY"]` — работает, но нет валидации: если переменная
  не установлена — упадёт в рантайме с невнятной ошибкой.
- `pydantic-settings` — читает `.env`, валидирует типы, падает **на старте**
  с понятным сообщением.

  ## База данных

| Окружение | БД | Почему |
|-----------|-----|--------|
| Local (dev) | SQLite | Ноль настройки, один файл, легко удалить и начать заново |
| Prod (future) | PostgreSQL | Продакшн-стандарт, конкурентность, типы данных |

**Почему не PostgreSQL сразу**
- Требует установки сервера, паролей, настройки соединения.
- Для пет-проекта и обучения SQLite покрывает 100% задач.
- Переход на PostgreSQL = поменять одну строку в `.env`
  (`DATABASE_URL=postgresql://...`). SQLAlchemy абстрагирует различия.

**Ограничения SQLite, о которых помним**
- Нет реального типа `ENUM` — используем `CHECK` constraint.
- Один писатель за раз (при записи блокируется вся БД).
- Нет нативных типов дат — SQLAlchemy эмулирует.
- Всё это неважно для одиночного пользователя на локальной машине.

**Почему не MongoDB / NoSQL**
- У нас чёткая реляционная схема: user — entries — game.
- Нужны JOIN'ы, уникальные составные ключи, CASCADE — всё это
  естественно для SQL и болезненно в NoSQL.

  ## UI

| Компонент | Выбор | Назначение |
|-----------|-------|------------|
| Фронтенд | Streamlit | Веб-интерфейс для библиотеки |

**Почему Streamlit, а не React / Vue**
- Пишешь на **Python** — не переключаешь контекст.
- Работающий UI — за 20 строк: форма, список, кнопки.
- Учимся автотестировать UI через Playwright — неважно, на чём написан фронт.

**Почему не HTML + Jinja2**
- Jinja требует серверного рендеринга: каждый чих — новый HTML.
- Много шаблонного кода.
- Streamlit — реактивный: изменил переменную — страница перерисовалась.

**Почему не React**
- JS + npm + сборка + стейт-менеджмент — это отдельный учебный трек.
- У нас цель — автотесты, а не фронтенд.
- Streamlit закроет 100% демо-задач.

**Ограничения Streamlit (принимаем)**
- Нельзя точно контролировать HTML — это влияет на локаторы в UI-тестах
  (будем использовать `data-testid` через st.markdown + HTML).
- Тяжёлый для больших приложений — не наш случай.

## Тесты

| Компонент | Выбор | Назначение |
|-----------|-------|------------|
| Фреймворк | pytest | Запуск и организация тестов |
| API-тесты | requests (sync) | HTTP-запросы к API |
| UI-тесты | Playwright | Управление браузером |
| Отчёты | allure-pytest | Наглядные HTML-отчёты |
| Покрытие | pytest-cov | Метрика покрытия кода |
| Фикстуры БД | pytest + SQLAlchemy | Очистка и наполнение БД |
| Параметризация | pytest.mark.parametrize | Много кейсов — один тест |

**Почему pytest, а не unittest**
- Меньше бойлерплейта: `assert x == y` вместо `self.assertEqual(x, y)`.
- Фикстуры — мощная система setup/teardown.
- Плагины (allure, cov, xdist) — под любую задачу.
- Стандарт в индустрии.

**Почему requests, а не httpx**
- `requests` — самый простой и распространённый.
- Синхронный — проще для новичка.
- `httpx` — если бы API-тесты были async. У нас — sync, потому что тесты и так быстрые.
- Оба покажут понимание HTTP-протокола.

**Почему Playwright, а не Selenium**
- Быстрее, стабильнее, современнее.
- Автоподгрузка браузеров одной командой.
- Встроенные ожидания (auto-wait) — меньше flaky-тестов.
- Запись действий (`codegen`) — быстрое прототипирование.
- Selenium — дольше настраивать, нужны драйверы, больше flaky.

**Почему Allure**
- Красивые HTML-отчёты: шаги, вложения, скриншоты, тренды.
- Интеграция с pytest — один плагин.
- Стандарт в командах, где есть автотесты.

## CI и инфраструктура

| Компонент | Выбор | Назначение |
|-----------|-------|------------|
| CI | GitHub Actions | Запуск линтера и тестов на push/PR |
| Хостинг кода | GitHub | Уже используется |
| Секреты | GitHub Secrets | Хранение `SECRET_KEY` в CI |
| Артефакты | Allure-отчёт как артефакт workflow | Скачивание после прогона |

**Почему GitHub Actions**
- Уже используем GitHub — 0 дополнительных сервисов.
- 2000 минут бесплатно в месяц для приватных репо, **бесконечно** для публичных.
- YAML-синтаксис, понятный новичку.
- Матричные сборки (тесты на Python 3.11 и 3.12).

**Почему не Jenkins / GitLab CI / CircleCI**
- Jenkins — надо хостить, настраивать, это DevOps-тема.
- GitLab CI — требует GitLab.
- CircleCI — ещё один сервис, ещё один аккаунт.
- GitHub Actions — минимум трения.

**Пайплайн (план)**
1. **lint** — `ruff check`, `ruff format --check`
2. **test** — `pytest --cov` с SQLite
3. **report** — публикация Allure как артефакт
4. Позже: **ui-test** — Playwright headless
5. Позже: **docker-build** — сборка образа
